# Nginx: мастер WebSocket + TLS

Пункт **Nginx (WS + TLS)** находится сразу под HAProxy в режимах whitelist и
node с Reality. Можно открыть его напрямую: `bash kto.sh nginx`.
После первой установки доступен локальный запуск без скачивания:

```bash
sudo /usr/local/sbin/kto-nginx
```

## Схема

Клиент VLESS WS+TLS -> Nginx -> обычный WS -> Xray или промежуточный релей.
TLS завершается на Nginx. Бэкенд не должен ожидать TLS, Reality или PROXY protocol.
Мастер не устанавливает Xray, не создаёт UUID и не меняет сервер выхода за релеем.
Участок Nginx -> бэкенд не шифруется этим конфигом; для защищённого backhaul нужен
отдельный туннель/доверенная сеть.

## Что потребуется

- Debian/Ubuntu с systemd, Python 3.10+, root и рабочий исходящий интернет.
- Назначенные машине IPv4 и уже настроенная маршрутизация с выбранного source IP.
- Домен и доступ к его DNS. Для HTTP-01 все A должны вести на выбранные IP этой машины.
- Входящий TCP :80 для HTTP-01 и выбранный TLS-порт (обычно :443).
- Backend IPv4:порт и одинаковый WebSocket-путь у клиента и бэкенда.
- На бэкенде разрешён вход с исходящего IP, который выберет мастер.

IPv6-listener, XHTTP, gRPC, Reality и HTTPS-бэкенды этот мастер не настраивает.
Если есть AAAA, он не начнёт новый HTTP-01 выпуск: проверь IPv6 или выбери DNS-01.
Существующие чужие сайты/сертификаты не удаляются и не импортируются автоматически.

## Установка

1. Выбрать **Поднять новый фронт**.
2. Ввести домен, один или несколько входных IP (можно номера из списка).
3. Указать backend, WS-путь, TLS-порт и исходящий IP. `auto` проверяет доступность
   бэкенда с локальных адресов, начиная с входных; затем фиксирует выбранный `proxy_bind`.
4. Выбрать сертификат: HTTP-01, DNS TXT вручную или готовые fullchain/key PEM.
5. Подтвердить план. При активном UFW отдельно подтвердить адресные allow-правила.

Показываются восемь этапов и ожидание длительных команд. Таймауты ограничены.
При недоступном бэкенде можно явно разрешить подготовку фронта заранее.
Это не будет отмечено как полностью рабочий маршрут.
`proxy_bind` применяется только к Nginx -> backend. apt и Certbot используют обычную
исходящую маршрутизацию машины; выбранный IP не меняет её для остальных процессов.

## Сертификаты

- Подходящий действующий сертификат переиспользуется. Для webroot сохраняется
  каталог из существующего renewal-конфига, чтобы не сломать продление.
- Для нового HTTP-01 сначала проверяется выдача уникального challenge по каждому IP,
  затем проходит staging-проверка CA и только после неё одна production-попытка.
- Локальный HTTP 200 не доказывает доступность сервера снаружи. Firewall провайдера,
  CDN и блокировку входящего :80 мастер обойти не может.
- При ошибке выводится различимая причина: DNS, чужой vhost, занятый порт,
  challenge 404, таймаут, rate limit. Бесконечного повторения выпуска нет.
- DNS TXT требует ручного ввода в DNS-панели и ожидания распространения до Enter.
  **Без DNS API/hook этот способ не имеет автоматического продления.**
- Готовый PEM должен соответствовать домену и ключу, иметь больше семи дней запаса.
  Конечная HTTPS-проверка дополнительно проверяет доверие к цепочке сертификата.
- Для Certbot подключается существующий timer (либо проверяется cron) и deploy-hook
  `nginx -t && systemctl reload nginx`. Автопродление зависит от исходного authenticator.

При multi-A на разных машинах одного локального challenge недостаточно. Нужна
синхронизация файлов на всех фронтах либо DNS-01; это не происходит само собой.

## Безопасность применения

- HAProxy, SSH, default route, DNS и глобальная политика firewall не меняются.
- Занятый другим процессом TLS-порт останавливает установку с указанием владельца.
- При существующем wildcard-listener Nginx используется общий сокет с ограничением
  нового vhost по `$server_addr`; чужие сайты остаются на своих адресах.
- Только на первой чистой установке отключается созданная пакетом default-заглушка.
- Чужой vhost с тем же `server_name` не перезаписывается. Сначала нужен ручной перенос.
- Конфигурация проверяется до reload; restart не используется. Отдельный nonce
  в проверочном ответе подтверждает, что применился именно новый config.
- При неудаче восстанавливаются прежние файлы и выполняется reload прежнего config.
  Если сервис до установки был выключен, неудачная установка возвращает его в stop.
- Установленные пакеты, уже выпущенный сертификат и явно разрешённые UFW-правила
  при откате не удаляются. Это сообщается в выводе.
- Сохраняются десять последних backup; незавершённая попытка остаётся черновиком.
  Чужие backup вне каталога мастера не затрагиваются.

## Лимиты и журналы

`worker_connections` повышается минимум до 8192, `worker_rlimit_nofile` минимум до
65536 и с запасом к уже настроенному большему числу соединений. Более высокие лимиты
сохраняются. Проверяются фактические лимиты активных workers. Это не обещание заданной
пропускной способности: нужны CPU, память, доступный бэкенд и подходящая сеть.

Логи созданных HTTP и HTTPS vhost находятся в `/var/log/nginx/kto/`.
Ротация: daily + maxsize 50M, четыре архива, проверка каждые пять минут.
50M не является жёсткой квотой: между проверками файл может вырасти больше.
Политики других журналов и существующих сайтов не меняются. При полном диске
мастер останавливается с причиной; пользовательские данные без согласия не очищает.

## Проверки и восстановление

- **Изменить / продолжить настройку** подхватывает черновик последней попытки.
- **Диагностика маршрута** показывает диск, DNS, source route, HTTPS и WS по каждому IP,
  прямой WS до бэкенда, таймеры и последние ошибки.
- **Проверить и восстановить настройки** повторно применяет сохранённый маршрут
  с полным набором проверок и backup. Если повреждён именно управляемый vhost,
  сначала восстанавливает его текст из сохранённого state и проверяет синтаксис.
  Исправленный файл сохраняется даже при последующей сетевой ошибке; runtime
  применяется только на этапе установки. Чужие сломанные configs не исправляет.
- **Удалить маршрут** удаляет только выбранный управляемый vhost и его state.
  Не останавливает Nginx и не удаляет общий сертификат. Старые WS завершаются естественно.

HTTP 101 проверяет WebSocket handshake, **не UUID, авторизацию VLESS или длительный
трафик**. Для итогового теста клиент должен проверить каждый IP отдельно, сохраняя
домен в SNI и Host. Настройки клиента выводятся после установки.

## Файлы

| Назначение | Путь |
| --- | --- |
| Мастер | `/usr/local/sbin/kto-nginx` |
| Vhost | `/etc/nginx/conf.d/kto-wss-ДОМЕН.conf` |
| Маршрут / черновик | `/etc/kto-nginx/sites/`, `/etc/kto-nginx/drafts/` |
| Backup | `/var/backups/kto-nginx/` |
| Журнал установки | `/var/log/kto-nginx.log` |
| Логи маршрута | `/var/log/nginx/kto/ДОМЕН.access.log`, `ДОМЕН.error.log` |
| Таймер логов | `kto-nginx-logrotate.timer` |

## Основания и тесты

Поведение сверено с [Nginx WebSocket](https://nginx.org/en/docs/http/websocket.html),
[управлением reload](https://nginx.org/en/docs/control.html),
[Certbot webroot/manual](https://eff-certbot.readthedocs.io/en/stable/using.html)
и [типами проверок Let's Encrypt](https://letsencrypt.org/docs/challenge-types/).

`python -m unittest discover -s tests -p test_nginx.py` проверяет валидацию, рендер,
конфликты, лимиты, сохранение webroot, откат, черновики и настоящий локальный WS-handshake.
Продакшн-CA, apt/systemd/UFW на пользовательском сервере тестами не запускаются.
